# The extension knows the teacher without a login

Teachers already sign in to AlurSekolah, and a second Nemu login would be one more password for every teacher at every school. So the Nemu Extension has no login of its own. The school operator types the school's install code into the extension's settings page once; the code is tied to the school's record (`school_install_code` → `workspace`). With every request the background sends that code and the email of the account signed in on the AlurSekolah page (`X-Nemu-Install-Code`, `X-Nemu-Email`). The Nemu Service refuses a request without a known code, and `schoolProcedure` matches the email against the school's WS-06 teachers: an unregistered account gets "Akun Ibu belum didaftarkan di Nemu." with a button that opens WhatsApp Web to the school's own WS-06 operator, the request ready for her to send (ID-02). Because the email is read from the page on every change, signing in as someone else switches who Nemu helps (ID-04). The same procedures still accept a W-SEKOLAH session, so the Admin Workspace and tests keep working.

Each AlurSekolah deployment marks up its account area differently, so the email comes from a small reader per site (the mock's `#menu-email`, the tenant's own). Sites without an AlurSekolah account (Ruang GTK, Moodle) ask as the last account seen on AlurSekolah, and signing out there clears it. We accept that anyone who can edit the page, or forge the headers with a valid code, can pose as a registered teacher of that school: for the MVP the code keeps other schools and strangers out, and nothing the extension can do is more than the teacher could do on the page. A login (Google or AlurSekolah OAuth) would close that gap and replaces the email, not the install code.
